# Scenarios

The sample data is generated by `uv run generate-data --scenario <name>`. Every scenario simulates 24 hours of
normal operation of the services `checkout`, `payment`, `catalog` and `auth` on the fixed date **2026-03-12 (UTC)**
and then adds an incident on top. The output is fully deterministic for a given seed (default `42`).

| Scenario | Story | Expected severity |
|---|---|---|
| `checkout-500` (default) | Bad `payment` deployment breaks checkout for legacy clients, no recovery | SEV-2 |
| `db-pool` | Traffic spike exhausts the `catalog` connection pool, auth deployment is a red herring, self-resolves | SEV-3 |
| `cert-expired` | TLS certificate of `payment` expires, every checkout fails from one instant on, auth deployment is a red herring, no recovery | SEV-1 |
| `api-outage` | External card processor Payvia is down for 75 minutes, about 4 in 10 checkouts fail, checkout deployment is a red herring, recovers on its own | SEV-2 |
| `memory-leak` | `catalog` v2.9.0 leaks memory, the platform kills the container at its limit four times and every restart drops requests, two memory-flavoured deployments are red herrings, still ongoing | SEV-3 |

Scenarios are functions registered in `SCENARIOS` in `src/incident_agent/data/scenarios.py`.

## Generating and switching scenarios

```bash
uv run generate-data --scenario checkout-500   # the default, same as running without --scenario
uv run generate-data --scenario db-pool
uv run generate-data --scenario cert-expired
uv run generate-data --scenario api-outage
uv run generate-data --scenario memory-leak
```

Each run overwrites `data/incident.db` (override with `--output`; `--seed` defaults to `42`). To switch back to
the default scenario, run `uv run generate-data` (or `--scenario checkout-500`) again. The MCP server opens a fresh
read-only connection per query, so it sees the new data right away; no restart is needed. A scenario never changes the
output of another one: `checkout-500` stays byte-identical whatever scenarios exist (pinned by a hash test).

Demo prompts (they do not name the cause):

| Scenario | Prompt |
|---|---|
| `checkout-500` | Since about 2 pm customers are getting 500 errors at checkout. What is going on? |
| `db-pool` | Since mid-afternoon (around 3 pm UTC) product searches have been slow or failing for some customers. What is going on? |
| `cert-expired` | Since about 3:20 pm UTC almost every checkout attempt is failing for our customers. What is going on? |
| `api-outage` | Earlier today, around 4 pm UTC, some customers could not pay at checkout. What happened? |
| `memory-leak` | Several times today, the first around 1:15 pm UTC, customers got errors on product pages for a minute or two. What is going on? |

## `checkout-500`

Expected severity: **SEV-2** ([severity.md](../.claude/skills/incident-runbook/severity.md)). Checkout is a core flow
and is degraded, not down: about 18% of its requests fail, which is in the 10-50% band, the errors are sustained and
still ongoing at the end of the day, and revenue is affected. It stays below the 50% line of SEV-1.

### What happens

A deployment of the `payment` service (v1.4.2) starts reading `payload["currency"]` without a default. Some
requests do not contain that field, so the charge handler raises `KeyError: 'currency'`. Checkout passes the
failure on to the customer as `HTTP 500`. About 18% of checkout requests fail from 14:03 until the end of the day.
There is no rollback.

Only **legacy clients** (`web-2.30.4`, `android-5.7.9`; `LEGACY_CLIENT_VERSIONS` in `data/util.py`) omit `currency`.
They are about 19% of the traffic (`web-2.31.0` 45%, `ios-5.8.1` 36%, `web-2.30.4` 11%, `android-5.7.9` 8%). In the
incident window a legacy request fails with probability 0.95 (so about 5% of them still succeed) and current clients
never fail from this bug: 0.19 x 0.95 = about 18% overall.

For every failed request:

- the `payment` service logs one ERROR line, the `checkout` service logs one `POST /checkout 500` ERROR line,
- both lines have the same `request_id` and the same `error_id`, pointing to one row in `errors`
  (stack trace, request context with `request_id`, `endpoint`, `client_version`, `http_status`),
- no `charge ok` line exists for that request, because payment crashed before charging.

Every `checkout` log line ends in `client=<version>`, before and after the incident:

- success: `POST /checkout 200 <latency>ms client=<version>` (INFO)
- failure: `POST /checkout 500 payment service error: KeyError: 'currency' client=<version>` (ERROR)

A request has exactly one `checkout` line (a failed request's INFO line is turned into the ERROR line, never
duplicated), so INFO plus ERROR lines per client equal that client's requests. The only other `checkout` ERROR
line, the one-off at 10:48, carries `client=` too.

### Timeline (UTC)

| Time | Event |
|---|---|
| 03:42 | Noise: one-off `TimeoutError` in `catalog` (search backend) |
| 08:17 | Noise: one-off `ValueError` in `auth` (malformed token) |
| 09:30 | Noise: deployment `catalog` v2.8.0 |
| 10:48 | Noise: one-off `ConnectionResetError` in `checkout` |
| 11:15 | Noise: deployment `auth` v3.1.1 |
| 12:26 | Noise: one-off `IndexError` in `catalog` |
| 13:12 | Noise: one-off gateway `TimeoutError` in `payment` |
| **14:01** | **Deployment `payment` v1.4.2** |
| **14:03** | **First `KeyError: 'currency'`** (first failure at 14:03:32 with seed 42) |
| 14:03 to 24:00 | About 18% of checkout requests fail with HTTP 500, all from legacy clients |

### Expected root cause

The `payment` deployment v1.4.2 at 14:01 introduced code that reads `payload["currency"]` without a default
(`demo_app/payment/charge.py`, `process_charge`; see [demo-app.md](demo-app.md)). Requests without a `currency` field raise `KeyError: 'currency'`
and checkout returns HTTP 500. The first error follows two minutes after the deployment and the rate stays
constant afterwards. The failures correlate with the client version: requests from `web-2.30.4` and `android-5.7.9`
fail (about 95%), requests from `web-2.31.0` and `ios-5.8.1` do not fail at all. With seed 42 the incident window
(from 14:03) has this checkout split:

| Client | OK | Failed |
|---|---|---|
| `web-2.31.0` | 1089 | 0 |
| `ios-5.8.1` | 846 | 0 |
| `web-2.30.4` (legacy) | 13 | 275 |
| `android-5.7.9` (legacy) | 7 | 158 |

The agent can reproduce this with `search_logs` alone: `service: checkout`, `query: "client=<version>"`, a `start`,
and `level: INFO` or `level: ERROR` with `limit: 1`; `total_matches` is the count. `get_error_stats` cannot split by
client. Proposed action: roll back `payment` to the previous version, or default the field
(`payload.get("currency", "EUR")`) and add a test. The agent proposes, the human decides.

### Red herrings

These are harmless or unrelated and should not be named as the cause:

- **Slow catalog queries:** a `WARN` roughly every 10 minutes all day, with or without the incident.
- **Auth token refresh retries:** a `WARN` roughly every 15 minutes all day.
- **Payment gateway retries:** a few `WARN` lines per day that succeed on retry.
- **Cache misses** in `catalog`: about 3% of catalog requests, `WARN`.
- **One-off errors before 14:00** in `catalog`, `auth`, `checkout` and `payment` (see the timeline).
  None of them is a `KeyError` and none repeats.
- **Older deployments:** `catalog` v2.8.0 (09:30) and `auth` v3.1.1 (11:15) are hours before the first error.

### Checking the data by hand

```bash
uv run generate-data --scenario checkout-500

sqlite3 data/incident.db "SELECT timestamp, exception_type, message FROM errors ORDER BY timestamp LIMIT 10;"
```

The command prints an hour-by-hour table of ERROR counts per service, where the jump at 14:00 is visible.

## `db-pool`

### What happens

A traffic spike hits the `catalog` service on `GET /search`. The search code takes a connection from a database
pool of **20 connections** (`pool_size=20`); at normal load about half of them are in use. When the load reaches
about twice the normal level the pool is full, requests wait for a connection and time out after 5 s:
`TimeoutError`, HTTP 504 (about 85%) or 503 (about 15%). The spike then decays and the errors stop on their own;
nothing is rolled back. Shortly before, the harmless `auth` deployment v3.2.0 (token TTL tweak) is the only change.

The normal catalog traffic has no `GET /search` lines, so this scenario adds a baseline search stream for the whole
day (about 285 lines per hour around 13:00, `GET /search?q=<term> 200 <n>ms`) and the spike on top as **real extra
INFO lines**. Load multiplier against that baseline (`load_multiplier` in `scenarios.py`):

| Phase | Time (UTC) | Load |
|---|---|---|
| normal | until 14:45 | 1.0x |
| ramp up | 14:45 to 15:15 | 1.0x to 3.6x |
| hold | 15:15 to 16:15 | 3.6x |
| decay | 16:15 to 16:55 | 3.6x to 1.0x |

The failure probability is zero up to the pool capacity (2.0x) and rises linearly to 45% at the peak, so errors
cluster in the peak and vanish as the load decays. A failed request has exactly one log line (the ERROR line, no INFO
line), linked to one `errors` row (`TimeoutError`, `timed out after 5.0s waiting for a connection from the pool
(pool_size=20)`, `request_context` with `request_id`, `endpoint: GET /search`, `client_version`, `http_status` 504 or
503; the ERROR line is logged 5 s after the request started). Stack frames are synthetic (`/app/catalog/...`, the demo
app has no catalog code). Successful searches get slower the closer the load gets to the capacity.

Pool `WARN` lines (about one per minute, no `request_id`) come first and continue during the peak:

- `connection pool usage high: in_use=16/20, waiting=0` while the load is between 1.6x and 2.0x (from 14:52),
- `connection pool exhausted: in_use=20/20, waiting=<n>` from the moment the pool is full (14:57), and during the peak,
- `connection pool back to normal: ...` once, after the decay.

### Timeline (UTC, seed 42)

| Time | Event |
|---|---|
| 03:42 | Noise: one-off `TimeoutError` in `catalog` (search backend, different message, no pool) |
| 09:30 | Noise: deployment `catalog` v2.8.0 |
| 10:48, 12:26, 13:12 | Noise: one-off errors in `checkout`, `catalog`, `payment` |
| 11:15 | Noise: deployment `auth` v3.1.1 |
| 14:45 | Search traffic starts to grow |
| **14:50** | **Deployment `auth` v3.2.0** (`chore(auth): extend refresh token TTL to 30 days`), red herring |
| 14:52 | First pool `WARN` (`usage high`) |
| **14:58** | **First pool timeout** (14:58:36), 8.6 minutes after the auth deployment |
| 15:15 to 16:15 | Peak: about 3.4x the baseline hour, 40-48% of search requests time out |
| 16:35 | Last pool timeout (16:35:25) |
| 16:46 | Last pool `WARN` (`back to normal`), no errors until the end of the day |

In total 555 search requests time out between 14:58 and 16:35 (1474 search lines in that window, about 38%). The
`auth` one-off `ValueError` of 08:17 is left out in this scenario, so `auth` has no ERROR line at all.

### Expected root cause

The connection pool of `catalog` (size 20) is exhausted by a traffic spike on `GET /search`. The proof is in the logs:
`search_logs` with `service: catalog`, `query: "GET /search"` and `limit: 1` returns the count in `total_matches` per
time window (about 72 per quarter hour at 13:00, about 245 at 15:30, back to about 70 after 17:00), the pool `WARN`
lines show `in_use=20/20, waiting=<n>`, and every error is a `TimeoutError` waiting for a connection. The errors
start when the load passes the pool capacity and stop when it decays. Proposed actions (never applied automatically):
raise the pool size or limit and queue requests, shed search load (rate limit, cache) and alert on pool usage. No
rollback is involved.

### Expected severity

**SEV-3** ([severity.md](../.claude/skills/incident-runbook/severity.md)). `catalog` is a non-core service and
checkout and payment are not affected, so the SEV-1 and SEV-2 criteria (core flow unavailable or degraded) do not
match. The "non-core service is degraded" criterion of SEV-3 does. The incident is resolved (the last window shows no
errors and the load is gone), so there is no uplift for an ongoing incident. The report should cite the numbers: about
38% of search requests failed between 14:58 and 16:35 UTC (about 1h40), none after that. The high error rate must not
push the rating to SEV-2, because that band is defined for core flows.

### Red herrings

- **`auth` deployment v3.2.0 at 14:50**, shortly before the first error. `auth` has no ERROR line all day, no change
  in request volume and no pool or timeout message. It is unrelated.
- **Older deployments:** `catalog` v2.8.0 (09:30) and `auth` v3.1.1 (11:15), hours before the incident.
- **Slow catalog queries and cache misses** (recurring `WARN` lines all day) and the one-off errors before 14:00.
  The one at 03:42 is also a `TimeoutError` on `GET /search`, but it is about the search backend, not the pool.

### Checking the data by hand

```bash
uv run generate-data --scenario db-pool
sqlite3 data/incident.db "SELECT * FROM deployments ORDER BY timestamp;"
sqlite3 data/incident.db "SELECT timestamp, message FROM logs WHERE message LIKE 'connection pool%' LIMIT 5;"
sqlite3 data/incident.db "SELECT MIN(timestamp), MAX(timestamp), COUNT(*) FROM errors WHERE message LIKE '%pool_size=20%';"
```

## `cert-expired`

### What happens

`checkout` calls `payment` over mutual TLS. The server certificate of `payment.internal:8443` has a `notAfter` of
**15:20:00 UTC** and nobody renewed it. From that instant every new TLS handshake of `checkout` fails and
checkout answers `HTTP 502`. About **98%** of the checkout requests fail (`CERT_FAILURE_PROBABILITY`); the other ~2%
ride on keep-alive connections that were opened before the expiry. All client versions are affected equally, which is
the contrast to `checkout-500` (only legacy clients fail). It is a step, not a ramp: 0% failures until 15:20:00, then
about 98%, until the end of the day. Nothing recovers and nothing is rolled back.

For every failed request:

- `checkout` logs one ERROR line, `POST /checkout 502 payment unreachable: SSLCertVerificationError: certificate has
  expired (notAfter=2026-03-12T15:20:00Z) client=<version>` (the request's INFO line is turned into it, never
  duplicated, and it ends in `client=` like every checkout line),
- it points to one `errors` row: service `checkout`, `SSLCertVerificationError`, message `[SSL: CERTIFICATE_VERIFY_FAILED]
  certificate verify failed: certificate has expired (_ssl.c:1006); payment.internal:8443 notAfter=2026-03-12T15:20:00Z`,
  `request_context` with `request_id`, `endpoint: POST /checkout`, `client_version`, `http_status: 502`,
- there is no `charge ok` line of `payment` for it, because the handshake failed and payment never saw the request.
  `payment` logs no error at all; its charge traffic simply stops (about 4 per minute before, a handful until 15:40).

The `notAfter` time is only in the error message (and the stack trace), so the agent can state it instead of inferring
it. Stack frames are synthetic (`/app/checkout/payment_client.py`, `ssl.py`): the demo app has no TLS code.

### Timeline (UTC, seed 42)

| Time | Event |
|---|---|
| 03:42, 08:17, 10:48, 12:26, 13:12 | Noise: the shared one-off errors (including the `checkout` `ConnectionResetError` at 10:48) |
| 09:30 | Noise: deployment `catalog` v2.8.0 |
| 11:15 | Noise: deployment `auth` v3.1.1 |
| **15:12** | **Deployment `auth` v3.3.0** (`chore(auth): rotate JWT signing keys`), red herring |
| 15:19:57 | Last successful checkout before the incident |
| **15:20:00** | **Certificate `notAfter`** |
| **15:20:05** | **First certificate error** (error_id 6), 8 minutes after the auth deployment |
| 15:20 to 15:30 | 42 of 42 checkout requests fail |
| 23:59:44 | Last failure of the day (error_id 1966), still failing |

With seed 42, from 15:20:00 until the end of the day, 2005 checkout requests are logged and **1961 fail** (97.8%); in the
hour 15:20 to 16:20 the share is above 97% too. `get_error_stats` shows the step in the `checkout` error rate.

### Expected root cause

The TLS server certificate of `payment.internal`, used by `checkout` to call `payment`, expired at 15:20:00 UTC
(`notAfter=2026-03-12T15:20:00Z`). The handshake fails with `certificate verify failed: certificate has expired` and
checkout returns 502. The proof is in the logs: one error message and stack trace for all failures, the first failure
5 seconds after `notAfter`, a 0% to ~98% step with no ramp, no client split, no payment error and no deployment that
fits. Proposed actions (never applied automatically): issue and install a new certificate for `payment.internal` and
reload payment, then check a handshake from checkout; add an expiry alert (for example 30 days ahead) and automate renewal.
Rolling back any deployment does not help.

### Expected severity

**SEV-1** ([severity.md](../.claude/skills/incident-runbook/severity.md)). Checkout is a core flow. About 98% of its
requests fail (1961 of 2005 since 15:20) and the last window still fails, so the flow is effectively unavailable and
more than 50% of its requests fail: the SEV-1 criterion. The SEV-2 band (10-50%, degraded) does not describe it, and if
criteria of several levels match the higher one wins. The incident is ongoing, so there is no downgrade for a resolved
incident. The report should cite the numbers: 1961 of 2005 checkout requests failed from 15:20:05 UTC, and it is not over.

### Red herrings

- **`auth` deployment v3.3.0 at 15:12**, 8 minutes before the first error and a plausible suspect (a security-related
  change, "rotate JWT signing keys"). How to tell it apart: `auth` has no ERROR line and no `errors` row all day, token
  validations continue at the normal rate, no trace has an auth frame, and the error text names a certificate of
  `payment.internal`, not a token or key. The failures also start at exactly `notAfter`, not at 15:12.
- **Older deployments:** `catalog` v2.8.0 (09:30) and `auth` v3.1.1 (11:15), hours before.
- **Slow catalog queries, auth token refresh retries, payment gateway retries, cache misses** (recurring `WARN` lines
  all day) and the **one-off errors before 14:00**, including the `checkout` `ConnectionResetError` at 10:48.
- **Not a client problem:** all four client versions fail at the same rate.

## `api-outage`

### What happens

`payment` charges cards through an external card processor, **Payvia** (`https://api.payvia.example/v1/charges`).
From **16:05:00 to 17:20:00 UTC** (75 minutes, `OUTAGE_START` / `OUTAGE_END`) Payvia is down: each charge attempt is
retried twice (3 attempts) and then fails, either with the provider's `HTTP 503 Service Unavailable` (about 65%) or with
a timeout of 5.0 s per attempt (about 35%). Of the checkout requests that start in the window, **40%** are drawn to fail
(`OUTAGE_FAILURE_PROBABILITY`; 42.7% realized with seed 42). The rest get through, so the outage is a large share, not
all. All client versions are affected alike, which is the contrast to `checkout-500`. It is a step in and a step out:
0% failures before 16:05:00, about 40% until 17:20:00, 0% from then on. **Nothing is deployed or rolled back at the
end:** the provider simply answers again. The incident is **resolved** at the end of the data.

For every failed request:

- `payment` logs one ERROR line, `Charge failed: ProviderUnavailableError: card processor Payvia returned HTTP 503
  Service Unavailable after 3 attempts (retries=2) POST https://api.payvia.example/v1/charges` (or `ProviderTimeoutError:
  card processor Payvia timed out after 3 attempts (retries=2, 5.0s each) ...`), and one `errors` row of service
  `payment`, endpoint `POST /charge`, with `http_status` 502 (503 case) or 504 (timeout case) in its `request_context`,
- `checkout` logs one ERROR line, `POST /checkout 502 payment failed: Payvia upstream 503 Service Unavailable (retries=2)
  client=<version>` or `POST /checkout 504 payment failed: Payvia upstream timeout (retries=2) client=<version>` (the
  request's INFO line is turned into it, never duplicated, and it ends in `client=` like every checkout line). It points
  to the same `errors` row as the payment line,
- there is no `charge ok` line of `payment` for it.

The cause is in the data and does not have to be inferred: provider name, upstream status text or timeout, and retry
count are in the error messages. Payment also logs `card processor Payvia health check failed: HTTP 503` (WARN) about
once a minute during the outage and one `card processor Payvia health check ok` (INFO) at 17:20:42, the first sign of
recovery. Log and error timestamps are the request times; the durations are in the text. Stack frames are synthetic
(`/app/payment/provider_client.py`): the demo app has no provider client.

### Timeline (UTC, seed 42)

| Time | Event |
|---|---|
| 03:42, 08:17, 10:48, 12:26, 13:12 | Noise: the shared one-off errors (the `payment` `card gateway timeout after 5.0s` at 13:12 does not name a provider) |
| 09:30 | Noise: deployment `catalog` v2.8.0 |
| 11:15 | Noise: deployment `auth` v3.1.1 |
| **15:55** | **Deployment `checkout` v2.7.1** (`perf(checkout): reuse HTTP connections to payment`), red herring |
| 16:04:50 | Last successful checkout before the incident |
| **16:05:00** | **Outage starts**, first failed health check |
| **16:05:12** | **First provider error** (error_id 6, HTTP 502, 503 from Payvia), 10 minutes after the deployment |
| 16:05:19 | First timeout (error_id 7, HTTP 504) |
| 16:05 to 16:35 | 71 of 156 checkout requests fail |
| 16:35 to 17:05 | 59 of 140 fail |
| 17:05 to 17:20 | 26 of 69 fail |
| 17:19:21 | Last failure (error_id 161) |
| **17:20:00** | **Outage ends** |
| 17:20:42 | `card processor Payvia health check ok` |
| 17:20 to end of day | No checkout error. 23:00 to 24:00: 0 of 70 requests fail |

With seed 42, 365 checkout requests are logged between 16:05:00 and 17:20:00 and **156 fail** (42.7%): 105 with HTTP 502
(provider 503) and 51 with HTTP 504 (timeout). Per client (failed / requests): web-2.31.0 61/148, ios-5.8.1 62/146,
web-2.30.4 18/43, android-5.7.9 15/28. `get_error_stats` shows the step in and the step out in the `checkout` and
`payment` error rates.

### Expected root cause

The external card processor Payvia, called by `payment`, had an outage from 16:05 to 17:20 UTC: it answered HTTP 503 or
timed out even after 3 attempts, so `checkout` returned 502 or 504. The proof is in the logs: the error messages name
the provider, its upstream status and the retries, the onset matches the first failed health check, there is no client
split, and the failures stop at 17:20 together with the first successful health check, without any deployment. Proposed
actions (never applied automatically): nothing to patch in this repository; ask the provider for its incident report,
alert on provider health and on 503/timeout rates, check customers whose charge failed for duplicate charges, and review
the retry and timeout policy (circuit breaker, fallback processor). Rolling back checkout v2.7.1 is not recommended: it
would not have changed the outage.

### Expected severity

**SEV-2** ([severity.md](../.claude/skills/incident-runbook/severity.md)). Checkout is a core flow. 156 of 365 requests
(42.7%) failed in a 75-minute window: the flow was degraded, not unavailable, and the share is inside the 10-50% band
and below the 50% line of SEV-1; the errors were sustained and affected revenue. The incident is resolved: the last
window is clean (0 of 70 in 23:00 to 24:00). The matrix says a resolved incident **may** be rated one level lower only
if the last window shows no errors **and the cause is known to be gone**. Here the cause is an outage at a third party;
the data shows that its answers returned, not why it failed or that it cannot recur, and a flow with about 4 in 10
failures for 75 minutes is not the short-lived SEV-3 case. So the expected level is SEV-2, and the report should say
that it is resolved and that no downgrade was applied. The scorer accepts exactly one level; because the downgrade is
optional, a live run that answers SEV-3 with that justification is a calibration finding, not a data error.

### Red herrings

- **`checkout` deployment v2.7.1 at 15:55**, 10 minutes before the first error and a plausible suspect (it changes how
  checkout talks to payment). How to tell it apart: checkout stays healthy for the 10 minutes between the deployment and
  the onset (50 requests, 0 failures); the failure rate is the same from the first to the last minute of the window, so
  nothing changes at the deployment; the errors name Payvia, its 503 or timeout and the retries, not a connection or
  deployment problem; the failures end at 17:20:00 with no deployment or rollback.
- **Older deployments:** `catalog` v2.8.0 (09:30) and `auth` v3.1.1 (11:15), hours before.
- **The shared `payment` noise:** the one-off `card gateway timeout after 5.0s` at 13:12, eight `gateway request timed
  out, retrying (attempt 1/3)` WARN lines spread over the day, slow catalog queries, auth token refresh retries and cache
  misses. None names Payvia or has a 503 or 3 attempts.
- **Not a client problem:** all four client versions fail at similar rates.

```bash
sqlite3 data/incident.db "SELECT COUNT(*) FROM logs WHERE service = 'checkout' AND level = 'ERROR' AND timestamp >= '2026-03-12T17:20:00Z';"
```

## `memory-leak`

### What happens

The `catalog` deployment **v2.9.0** (10:20 UTC, `feat(catalog): add product comparison endpoint`) leaks memory at a
constant **1.75 MiB per minute** (105 MiB per hour). The container limit is **512 MiB**, so after 176 minutes of uptime
(204 MiB to 512 MiB) the platform kills it (`OOMKilled`, exit code 137). It is down for **120 seconds**, comes back at
204 MiB and climbs with the same slope again. Four kills fit into the day (13:16, 16:14, 19:12, 22:10); the leak is
still running at the end of the data (381 MiB at 23:55, the next kill would be at 01:08). Nothing is rolled back.

`catalog` (286 lines), `auth` (288) and `payment` (288) log their memory use, one line every 5 minutes

`checkout` has no memory line, because every `checkout` log line must end in `client=<version>`. From 85% of the limit the line is a `WARN` (`memory usage high: ...`, 34 of them, the first at
12:35). `auth` (limit 256 MiB) and `payment` stay flat all day: they are the control group (`auth` and `payment`, not `checkout`). `catalog` is flat at about

back to the base at every restart. Logged values carry a jitter of 3 MiB; no line is logged while the container is down.

Platform lines of `catalog` (no `request_id`): `container killed by the platform: OOMKilled (rss=512MiB limit=512MiB
exit_code=137)` (ERROR) at every kill, `catalog v2.9.0 started (restart <n> after OOMKilled), ready after 120s` (INFO)
when it is back, and a start line for the two deployments (09:30 and 10:20; deployments are rolling, there is no
downtime).

During a restart **every** `catalog` request fails (`kill <= time < kill + 120 s`). The request line is turned into one
ERROR line, `GET /products/<id> 503 ConnectionRefusedError: app container of catalog is restarting`, linked to one
`errors` row (`ConnectionRefusedError`, `[Errno 111] Connection refused: app container of catalog is restarting`,
`http_status` 503, synthetic frames in `/app/catalog/ingress.py`, the sidecar that stays up). The error text does not say
why the container restarts. The failed requests use no random draw, so the total depends only on the shared traffic and
the four fixed windows. `checkout`, `payment` and `auth` have no new error.

### Expected root cause

`catalog` v2.9.0, deployed at 10:20, leaks memory: the resident memory grows by about 1.75 MiB per minute until the
512 MiB limit, the platform kills the container (OOMKilled) and every request fails while it restarts. The proof is in
the logs and takes three steps: the `catalog` errors come in four 2-minute bursts and name a restarting container, an
`OOMKilled` line sits at the start of every burst, and the `memory usage` lines of `catalog` are flat until 10:20 and
then a straight line that falls back to the base at each restart with the same slope. **Dating the leak** is the hard
step (the scorer does not check it, see the known limits below). The deployment message says nothing about memory and the first symptom comes 2 hours 56 minutes later, but the
data settles it three ways: the memory is flat after 09:30 and after 13:04, the slope starts at 10:20, and the time from
a restart to the next kill is 176 minutes, so kill 1 (13:16) minus 176 minutes is exactly 10:20:00. Proposed actions
(never applied automatically): roll `catalog` back from v2.9.0 to v2.8.0, or find and bound what v2.9.0 keeps in memory
(the repository has no catalog code, so there is no patch); restart `catalog` before it reaches the limit until then;
alert on memory above 80% of the limit and on `OOMKilled`.

### Expected severity

**SEV-3** ([severity.md](../.claude/skills/incident-runbook/severity.md)). Only `catalog` fails, and the matrix calls
`catalog` and `auth` non-core "unless they block checkout or payment", which nothing in the data shows. The rows:

- SEV-1 "A core flow is unavailable, or more than 50% of its requests fail, or there is data loss, a security issue or
  payment integrity risk": no core flow is touched.
- SEV-2 "A core flow is degraded, 10-50% of its requests fail, errors are sustained or ongoing and affect revenue": no
  core flow is degraded.
- SEV-3 "A non-core service is degraded, or a core flow has under 10% failures or only a short-lived problem, and a
  workaround exists": **matches.** `catalog` is non-core and degraded (four outages of 2 minutes, 102 of 10,076 requests,
  1.0%), and a retry after about 2 minutes works.
- SEV-4 "Cosmetic issues, isolated errors, background noise": the errors recur four times and are not isolated; if
  criteria of several levels match, the higher one wins.

The incident is **ongoing** (memory still rising), which the report should say, but "an ongoing incident ranks higher
than a resolved one" gives no extra level here because no core flow is involved. It would become SEV-2 if checkout
depended on `catalog` and failed with it.

### Red herrings

- **`auth` deployment v3.4.0 at 13:04**, 12 minutes before the first kill, and its message says "in memory": the most
  tempting suspect for a reader who looks at the deployments list for the last change before the first error. How to
  tell it apart: `auth` memory is flat before and after it, `auth` has no error, the container that is killed is
  `catalog`'s, and kills 2 to 4 happen hours after the last deployment of the day.
- **`catalog` deployment v2.8.0 at 09:30** (`add category index cache`), a cache and so a typical leak suspect: the
  `catalog` memory stays flat at about 204 MiB for the 50 minutes after it; the rise starts at 10:20.
- **`auth` v3.1.1 (11:15)**, hours before; `auth` memory is flat.
- **Not traffic:** kill 4 happens at 22:10 when traffic is at 40% of the peak, with the same 176-minute cadence as in
  the busy hours, so the slope does not follow the traffic curve.
- **Shared noise:** the one-off errors (the `catalog` `IndexError` at 12:26 and the `payment` timeout at 13:12 are close
  to kill 1 and unrelated), slow queries, cache-miss warnings and token refresh retries.

### Known limits of the scorer

- `root-cause-named` needs `catalog`, `v2.9.0` and leak or growth wording: `leak`, `unbounded`; or `memory`,
  `memory usage`, `memory consumption` or `rss` followed within three words (no punctuation between) by grow\*,
  climb\*, rise/rises/rising/rose/risen or increas\* ("memory usage is growing", "RSS grows linearly"); or
  growing, climbing, rising or increasing followed within two words by `memory` or `rss` ("ever-growing memory").
  Matching is case-insensitive. A cause statement with only the symptom (OOM, out of memory, container killed,
  "traffic grows and the container runs out of memory") fails. The word windows are loose: "traffic is rising and
  memory ..." would also match, and a negation ("memory is not growing") is not read.
- The scorer cannot check that the agent dated the knee at 10:20 from the memory trend and the restart cadence. And
  `v2.9.0` is also the latest `catalog` deployment, so an agent that reads only the deployments list for the failing
  service finds the right version without any analysis. The version is therefore not what discriminates; the parts
  that do are the red herrings (`auth` v3.4.0 and `catalog` v2.8.0 must not be in the cause statement, and `auth`
  v3.4.0 must be ruled out) and the growth wording. Whether that wording rests on the memory lines is read by a human.
- `counts-reconciled` only looks for 102 anywhere in the report and is a warning; all catalog ERROR lines are 108.
- The scorer cannot read derived numbers or statements. Observed in the first live calibration (2026-10-19, 2 runs,
  both PASS): one report stated a slope of 1.9 to 2.0 MiB per minute, but the data has 1.75; and one report called the
  incident "resolved at the last window" without reading the end-of-day memory lines (the memory was still rising, the
  next kill is due at 01:08). Both
  passed every check. A human has to read them.
